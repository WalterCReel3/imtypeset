[from reviewer-4] public-api review 1/5 (highest cost): Text() finds its layout by the text POINTER — breaks under every binding and leaks cache; fix before release
All READ from src/imtypeset.cpp unless marked INFERRED. Nothing was run.

A1. The cache key is pointer identity. text_widget(): `widget_for(*ctx, ImGui::GetID(static_cast<const void*>(text)), frame)`. ImGui itself hashes string CONTENT for IDs and uses pointer IDs only where the caller explicitly says PushID(ptr). Consequences:
 - Temporaries / bindings. `ImTypeset::Text(std::string(...).c_str())`, `Text(fmt::format(...).c_str())`, and any Python binding: pybind11/litgen converts `str` to a `const char*` through a temporary std::string per call (INFERRED, from memory of pybind11's string caster; litgen was not run). The pointer is then whatever malloc returns that frame. If it differs from last frame the ID differs: a NEW slot, a full text build + total-fit layout, every frame. The stated contract (0 layouts on the second frame) silently becomes allocator-dependent for the Python audience the premises name as a goal.
 - Leak. A slot is forgotten only after FORGET_AFTER_FRAMES = 600 unused frames, swept every 64, and POOL_LIMIT is 16. A call site whose pointer changes each frame therefore holds ~600-664 dead ImTypesetParagraph objects (each with text copy, node arena, commands, line index). 20 such paragraphs = ~13,000 live paragraph objects in steady state. No cap on ctx.widgets anywhere.
 - Same in plain C++ when a std::vector<std::string> reallocates or a string grows: every paragraph is re-laid-out that frame and the old slots linger 10 s.
 - Stack buffer reused in a loop (`char buf[256]; for(...) { snprintf(buf,...); ImTypeset::Text(buf); }` with no PushID): same ID each time, so slots are assigned by ORDER of use in the frame (uses_this_frame). Correct while the list is stable; insert or remove one row at the top and every row below it mismatches its slot -> N text builds + N layouts in one frame. With ImTypesetTextFlags_NoTextCompare the same loop shows STALE TEXT (pointer equal, so `fresh` is false and the bytes are never looked at). The header's promise wording covers it, but a freed-and-reallocated heap string at the same address breaks the promise without the host doing anything it can see.
 - NoTextCompare + text_end: not-fresh path only re-sets when `text_end != nullptr && size != given_size`; going from an explicit text_end to NULL keeps the old shorter text.
 - Identical literals merged by the linker / same string in two table columns: handled by the n-th-use slot; fine. Order-dependence again if one of them is conditional.
Why this is the expensive one: NoTextCompare, BytesCompared in ImTypesetStats, and the header paragraph "found again by the `text` pointer and the ID stack" all publish pointer identity as API. Changing the key later (to a content hash, or to an explicit `const char* str_id` as ImGui::InputTextMultiline / BeginChild take) changes documented behaviour and a flag's meaning. Decide now. A content-hash key costs the same O(bytes) the default path already pays in memcmp+strlen, and makes Text() work identically from C++, Python and C.

A2. Even with the cache working, the default path is O(total bytes submitted) per frame for OFF-SCREEN paragraphs (strlen + memcmp before the visibility test). Only NoTextCompare gets "costs the same whatever its length", and that flag is unusable from a binding per A1.

A3. `ctx->stats.BytesCompared += (int)...` and `VerticesEmitted += ...` are plain `int` accumulators "since the context was made". A 100 KB document at 60 fps is 6 MB/s compared: signed overflow (UB; UBSan would report) after ~6 minutes. VerticesEmitted at 40k vertices/frame overflows in ~15 minutes. ImTypesetStats is a public struct, so the field type is a promise: either the counters are per-frame (reset in a frame hook) or they are 64-bit/unsigned. The tests run a handful of frames and cannot see it.

[from reviewer-4] public-api review 2/5: defects reachable today through the header (errors that are lost, a null-context crash, legacy backends, Windows paths)
All READ (file:symbol) unless marked. Nothing was run. Ranked.

B1. A failed CreateContext is invisible when a context is already current. CreateContext() writes `global_error()`; GetLastError() returns `error_of(g_context)`, i.e. the CURRENT context's error. Call: have a context current, then `CreateContext("0.0.0")` -> returns NULL, `GetLastError()->Code` is whatever the current context last recorded (None on a fresh one). tests/test_api.cpp create_context_refuses_... only checks the code while no context is current.

B2. GetLastError() is sticky and there is no way to clear it ("Code is None until one has failed", never reset). Combined with void functions (Text, TextJustified, DrawParagraph, DestroyParagraph) and LayoutParagraph returning a size, a host cannot ask "did THIS call fail". Needs either clear-on-success semantics stated per function or a ClearLastError(); the choice is API.

B3. Text()/TextJustified() cannot report anything. text_widget() never writes ctx->error, and the slot's paragraph is unreachable, so TextTooLong, LayoutFailed, a refused formula (once api-math lands: MathRefused with its byte/codepoint position — the whole point of refusal reporting) and the no-font fallback are all silent from the widget entry, which is the entry most hosts will use.

B4. Null ImGui context crash despite "Nothing reachable from data asserts"/"all work with no context". draw_args() -> ink_of() -> `ImGui::GetColorU32(ImGuiCol_Text)` whenever style Color == 0 (the default), and .deps/imgui/imgui.cpp GetColorU32 dereferences GImGui unconditionally. DrawParagraphToBuffers is advertised for "a host that has no ImDrawList", exactly the host likely to have an odd context lifetime.

B5. Wrong ImGui context is not detected on the draw side. add_font() refuses when `ImGui::GetCurrentContext() != ctx->imgui`; text_widget() only checks for null, and DrawParagraph checks nothing. With a second ImGui context (own atlas) current, Text() lays out with context A's ImFont* and emits its UVs into a draw list textured by B's atlas: garbage glyphs, no error. Conversely the binding is to the ImGui CONTEXT although fonts belong to the ATLAS: two ImGui contexts sharing one atlas (a supported ImGui pattern, CreateContext(shared_font_atlas)) cannot share an ImTypeset context's fonts through add_font's check even though it would work. Decide which the binding is; the header says "bound to the current ImGui context. Fonts go into that ImGui context's atlas".

B6. A backend without ImGuiBackendFlags_RendererHasTextures is "required" in prose and checked nowhere (grep: the flag name appears in src/ only inside one error string). On such a backend the atlas is Locked during the frame; imgui_draw.cpp ImFontAtlasBakedGetOrAdd then returns the CLOSEST baked size, or hits `IM_ASSERT(!atlas->Locked && "Cannot use dynamic font size...")` and returns NULL. src/draw.cpp bake() takes `state.size = state.baked->Size; state.scale = 1.0f` — so glyphs are drawn at the closest baked size on positions computed for the requested size: overlapping or gappy text with no error, or an ImGui assert. Many in-house engine backends are still pre-1.92-texture. Text() already has a fallback path for "no font"; this case deserves the same or a refusal with a reason. (Behaviour INFERRED from the two sources; not run.)

B7. Windows paths. add_font() and FontLibrary::register_font (src/fontlib.cpp) open with `std::fopen(filename, "rb")`. ImGui's own AddFontFromFileTTF goes through ImFileOpen, which converts UTF-8 to wide on Windows and honours IMGUI_DISABLE_DEFAULT_FILE_FUNCTIONS. A font under C:\Users\<non-ASCII name>\ loads in ImGui and returns FileNotFound here. INFERRED for Windows (GCC/Linux only was built); the two fopen calls are READ.

B8. Explicit colours ignore style.Alpha. ink_of(): Color==0 -> GetColorU32(ImGuiCol_Text) which multiplies by style.Alpha; a non-zero ImTypesetStyle::Color or ImTypesetRun::Color is used raw. Inside BeginDisabled() or a fading window the default ink dims and every coloured run (links, code spans) stays at full alpha.

B9. GetParagraphError goes stale across widths. p.error is reset only in build_material(); layout_paragraph() sets LayoutFailed `if p.error.code == None` and never clears it. Lay out at width A (fails), then at width B (succeeds, no rebuild): GetParagraphError still says LayoutFailed.

B10. A paragraph with no usable font is invisible through the paragraph API: layout_paragraph returns early on p.fallback, size (0,0), DrawParagraph draws nothing, DrawParagraphToBuffers returns TRUE. Only Text() falls back to ImGui text. The two entries disagree about the same condition.

B11. DestroyParagraph is O(paragraphs): std::find + vector erase over ctx->paragraphs. A document host that frees 100k paragraphs one by one pays ~10^10 element moves/compares. Also it looks the handle up in the CURRENT context while every other paragraph function uses p->ctx: destroying a paragraph of a non-current context is refused (leaks until that context dies) with the error written to the wrong context.

B12. One-entry memo in line_height_of(): two styles with different LineHeight used alternately in a frame (heading/body via LayoutParagraph(style)) run snprintf+strtod on every call. Not an allocation, but it is the "free when nothing changed" path.

[from reviewer-4] public-api review 3/5: declarations that are promises — shape, ABI and binding problems in include/imtypeset.h
READ = include/imtypeset.h + src/imtypeset.cpp + .deps/imgui; implot is from MEMORY (no source in tree); litgen/cimgui behaviour is INFERRED, nobody ran either. Ranked by cost if shipped.

C1. Indices are public when they need not be. ImTypesetSelection, HitTestParagraph, GetParagraphLength, SelectParagraphRange all trade in "positions in what was shipped for one paragraph at one width". The header warns at length; the API still makes misuse the path of least resistance: (a) a stored selection silently means something else after any reflow — indices are clamped, nothing detects staleness, no layout serial is exposed; (b) by the builder's own finding an index EQUALS the byte offset in justified ASCII, so the bug passes every casual test. p.index_bytes already maps both ways and is monotone, so every public function could take and return text byte offsets and keep indices internal; a selection would then survive reflow by construction and the 9-line warning disappears. This contradicts the standing ruling in docs/port-hazards.md ("the public header says so wherever it exposes an index"). I disagree with that ruling for the public surface: documented-not-prevented is the wrong side for a type that cannot be withdrawn. If indices stay, at least return a layout serial with them.

C2. Byte offsets everywhere, no codepoint option: ImTypesetRun::Start/End, GetParagraphTextOffset, GetParagraphIndexFromTextOffset. Python/C#/JS strings are not UTF-8 byte arrays; every binding user must encode and count bytes to style a word. ImTypesetErrorInfo already reports both BytePos and CodepointPos, so the library accepts that hosts need both — but only on output.

C3. CreateContext carries the build check in its own signature (5 defaulted parameters, four of them `(int)sizeof(...)`). ImGui keeps CreateContext(ImFontAtlas* = NULL) clean and does the check in a separate DebugCheckVersionAndDataLayout behind IMGUI_CHECKVERSION(); ImPlot::CreateContext() takes nothing (memory). Costs: (a) adding one more check later changes CreateContext's signature for every binding; (b) no room left for the parameter it will actually want (an ImFontAtlas*/ImGuiContext*, see B5); (c) a C binding has no default arguments, so a C caller types five arguments by hand; a generated Python binding evaluates the sizeofs in the BINDING's translation unit, which is the right TU, but the stub shows `sizeof_imwchar: int = 4`-style parameters to end users (INFERRED). (d) Only ImTypesetStyle is size-checked; ImTypesetRun — the one struct the host passes as an ARRAY, where a stride mismatch reads garbage — and ImTypesetSelection are not.

C4. CreateContext always makes the new context current (tested: `GetCurrentContext() == second`). ImGui::CreateContext restores the previous current context if there was one (.deps/imgui/imgui.cpp, "Restore previous context if any, else keep new one"); ImPlot sets current only if none (memory). A host that creates a second context for a second window gets its first one silently switched away. Documented, but it is the opposite of the convention the header says it follows, and it is a behaviour change to fix later.

C5. `ImTypeset::Text(const char* text, const char* text_end = NULL, flags)` has the name of ImGui's printf entry and the signature of ImGui::TextUnformatted. `ImTypeset::Text("%d items", 0)` compiles (literal 0 is a null text_end) and prints "%d items". ImGui's name for this shape is TextUnformatted; if a printf entry is ever wanted, the name Text is gone. In bindings `text_end` becomes an unrelated second string: `text_end - text` is then an arbitrary size and set_text copies/memcmps up to 16 MiB from a foreign pointer (INFERRED; same hazard in ImGui's own bindings, which special-case it — SetParagraphText and Text need the same special-casing and nothing records that).

C6. TextJustified() is Text() with Align forced — and ImTypesetStyle's default Align is already Justify, so by default the two public functions are the same call. Meanwhile there is no way to give Text() a style, a wrap width or an alignment per call other than mutating GetStyle() and restoring it by hand; ImGui and ImPlot both use Push/Pop for that. One redundant function is public; the mechanism hosts will need is absent.

C7. ImTypesetLayoutFlags_FirstFit and _TotalFit are two bits for one three-way choice (default / first fit / total fit). Both set: TotalFit wins (layout_paragraph: first_fit only `&& !block.ragged_total_fit`), undocumented. This should be an enum value or one flag; as flags the contradictory state is expressible forever.

C8. Public things that do nothing yet: ImTypesetTextFlags_Math ("No effect yet") and the `face_index` parameter of both AddFont functions (anything but 0 refused). Each is a promise about future semantics made before the feature exists; api-math is about to define the first, font-wild the second. If either lands differently the published signature is wrong. Also ImTypesetStats::BytesCompared / TextBuilds publish implementation details of the pointer cache (see review 1/5).

C9. Fixed role set. ImTypesetFace_ is seven hard-wired roles (CodeBold but no CodeItalic; no heading/second family) with COUNT in the enum, and MergeMode is refused with nothing in its place: a character no face has is U+FFFD. The first CJK, emoji or icon-font user has no route. Not fixable in this task, but the enum-as-closed-set is the declaration that makes it hard later.

C10. Smaller: enum values other than the first are implicit (ImTypesetError_ especially — bindings and logs will hard-code numbers; append-only must be stated or values written out). GetStyle() with no context returns a writable static `orphan` and writes are silently lost (ImGui asserts). `ImVector<ImDrawVert>*`, `ImVector<ImDrawIdx>*`, `ImVector<ImVec4>*` are template instantiations in signatures while the header comment says it "declares no template" — true literally, but a C binding needs the three ImVector_ typedefs generated; ImGui has precedent (ImFontGlyphRangesBuilder::BuildRanges), so acceptable, just not free. HitTestParagraph returns only an index: no way to tell a click on text from a click in the margin (needed for links and click-to-deselect).

What is good and should not be lost: opaque handles, POD structs returned by const pointer from library-owned storage (ErrorInfo, Stats — extensible without ABI break), no STL, no callbacks/unions/bitfields/overload sets, ImGui-style flags typedefs, every entry tolerating null. The surface is binding-shaped; the problems above are semantic, not syntactic.

The header's "A paragraph whose rectangle is clipped draws nothing" is true; "O(visible)" is true of vertices only. D3. Baseline. text_widget() places the paragraph with ImGui::Dummy(p.size): ItemSize with no text baseline offset. `ImGui::Button("x"); ImGui::SameLine(); ImTypeset::Text("label");` puts the text FramePadding.y higher than ImGui::Text would, and in a table row containing framed widgets it does not sit on the row's text baseline. A line is also 1.35 em tall where ImGui's is the font size, so one-line labels do not match neighbours either. Public imgui.h has no way to pass a baseline offset, and no ImTypeset function exposes the first baseline so a host could correct it. (INFERRED from ImGui's ItemSize/TextEx, read in memory, Dummy read in imgui_widgets.cpp; the builder says SameLine/tables were not run.) The header says "Works in ... tables" — by construction for clipping, not for alignment.

D4. The item is always the full available width (justified box width = line width), even for three words of left-aligned text: IsItemHovered() is true across the whole row, SameLine() after it has no room, and in an auto-resizing window or tooltip the paragraph both reads its width from the window and dictates it. There is no wrap-width override for Text(). Also size.x = ceil(width): with a fractional GetContentRegionAvail().x (docking splits, FontScaleDpi-scaled indents) the item is up to 1 px wider than the space, which in a window with ImGuiWindowFlags_HorizontalScrollbar is enough to summon the scrollbar (INFERRED).

D5. Fonts the host removes or the atlas clears. ctx->added[] / ctx->fonts hold raw ImFont*. `io.Fonts->Clear()` or `RemoveFont(font)` (the header hands the pointer out and says "the atlas owns it") leaves them dangling; the next Text() dereferences freed memory in src/draw.cpp bake(). There is no RemoveFont/ClearFonts here and no warning in the header. Re-adding a role leaves the old ImFont in the atlas for good (a font-picker UI leaks one atlas font per pick). Also: a font added between LayoutParagraph and DrawParagraph draws one frame of old positions with the new font (drawable() does not compare generations) — cosmetic.

D6. Threads. G. MINIMALISM.
 Should not be public yet (cannot be withdrawn): ImTypesetTextFlags_Math while it does nothing; `face_index` while every value but 0 is refused; TextJustified (identical to Text under the default style); ImTypesetStats::BytesCompared and TextBuilds (cache internals); IMTYPESET_IMGUI_VERSION_NUM + GetImGuiVersionNum (kept, per the builder, because tests/smoke.cpp uses it — a test is not a reason for a public symbol); ImTypesetLayoutFlags as two bits (C7); ImTypesetSelection-as-indices (C1).
 Missing, ranked by how soon a first user hits it:
  1. Per-call style / wrap width / alignment for Text() (Push/Pop or a parameter). Today: mutate GetStyle() and restore by hand; no wrap width at all.
  2. Characters outside the face: CJK, emoji, icons. MergeMode is refused and nothing replaces it.
  3. One-shot measure without a handle (ImGui::CalcTextSize analogue): width + text -> size/line count. Possible today only via Create/Set/Layout/Destroy.
  4. Line geometry: rect and baseline of line i, caret rect for a position, first baseline. Needed for carets, scroll-to, host-side clipping of long documents, and to fix D3 from outside.
  5. An explicit-ID or content-keyed widget entry that works from bindings (A1).
  6. A selectable-text helper (mouse -> selection -> clipboard). Everything needed is public but every host will write the same 40 lines; deliberately omitted per D30 — I would rank it below 1-5, not out.
  7. Font removal/replacement (D5), and adopting an ImFont the host already added.
  8. Codepoint (not byte) offsets for runs and conversions (C2).
 Present and right: measuring/line count via the paragraph, colour per run, selection highlight drawing, copy text, text-offset conversion.

OVERALL. The surface is well-shaped syntactically — opaque handles, POD, no STL, no callbacks, null-tolerant, errors as data — and the validation funnel holds: I found no host number that reaches arithmetic unclamped. It is not ready to be called stable because of four semantic choices that are cheap today and breaking later: pointer-keyed Text() (1/5), public indices (C1), CreateContext's signature and make-current behaviour (C3, C4), and the error model's stickiness and blind spots (B1-B3).

(1) The pybind11/litgen pointer behaviour in A1 is from memory; the C++ temporaries case is certain from the source, the Python severity is not — someone should run litgen on the header and call Text() twice with a 40-character str. (4) FontRasterizerDensity != 1: I could not decide by reading; nobody has run it.
